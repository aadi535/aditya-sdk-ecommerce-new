# Hosting APEX

Deployed storefront: https://apex-ecommerce-aditya.vercel.app

Public API origins:

- Users: https://apex-users-aditya.onrender.com
- Products: https://apex-products-aditya.onrender.com
- Orders: https://apex-orders-aditya.onrender.com

These services use Render's free tier. The current database was created on 29 October 2026 and expires after 30 days. Arrange migration or a paid database before expiry for continued account and order persistence.

The frontend runs on Vercel. Three Docker web services (Python users/auth, PHP products, Java orders) and PostgreSQL run on Render. This preserves the project’s microservices architecture. Vercel does not run the Docker Compose stack.

## Render

1. Create a Blueprint instance from this repository, using `render.yaml`.
2. Select the deployment branch containing this file.
3. Set each `ALLOWED_ORIGINS` field to the exact Vercel origin (no trailing slash), for example `https://apex-ecommerce-aditya.vercel.app`.
4. Set the orders service `USERS_API_URL` to the users service’s public HTTPS URL. Free Render web services cannot receive private-network traffic.
5. The Blueprint provisions three Free web services and a Free Postgres database. Review the plan summary before deploying. Free databases expire after **30 days** and are eventually deleted; use a paid database or migrate/export before expiry if you need long-term persistence. Free services sleep when idle, share the workspace’s free-hour allowance, and may take a minute or longer to wake up.
6. Deploy users first so its startup transaction initializes the schema and sample catalog, then products and orders. If orders starts before initialization, redeploy it after users is healthy.

Database credentials are generated by Render and referenced through Blueprint environment variables. No credentials belong in Git. The database’s public IP allow list is empty; services connect through Render’s internal database network.

The users service runs `schema.sql` inside a transaction under a database lock at startup. It uses non-destructive `CREATE IF NOT EXISTS` and inserts missing sample catalog rows. It never seeds an account, default password or demo order. This initializes a new deployment; it is not a replacement for versioned migrations when changing an existing schema later.

## Vercel

Import the repository with the repository root as Root Directory. Root `vercel.json` installs and builds `frontend` and publishes `frontend/dist`.

Set these public build-time variables for Production, using the actual Render HTTPS origins:

- `VITE_USERS_API_URL`
- `VITE_PRODUCTS_API_URL`
- `VITE_ORDERS_API_URL`

Redeploy when any of these change. They are endpoint addresses, not secrets. Never put a database password or API secret in a `VITE_` variable because it is embedded in browser code.

## Accounts and orders

Visitors register a real account with a valid email format and at least eight password characters. Passwords are hashed with PBKDF2. Random session tokens are hashed in PostgreSQL, expire after eight hours and are invalidated on logout. The browser keeps its token in session storage. There is no password reset or email verification in this educational project; use a unique demo password.

`GET /users` was removed: public access to password hashes is not appropriate. `GET /me` returns only the authenticated user. Orders verify the current session through the users service. A customer only sees their own orders. Admin-only status changes are checked by the server. Checkout accepts product IDs and quantities; the Java service locks stock rows, calculates prices from the catalog, and atomically saves totals and line items while reducing stock. No card information or payment is collected.

To grant an admin role, use a database console under your control:

```sql
UPDATE "User" SET role = 'admin' WHERE email = 'your-admin-email';
```

Register the intended admin account first. Role changes take effect when the backend verifies the next request; log in again to refresh the frontend’s admin button. Do not publish an admin password.

## Local development

`docker compose up --build` starts the database, initializes the schema via the users service, and runs the three APIs and frontend. The old Prisma migration runner is retained under the optional `legacy-migrations` profile for historical reference; do not run it against the new initialized schema.

The frontend uses `VITE_*_API_URL` variables, defaulting to the original localhost ports during development. The users service accepts `DATABASE_URL` or the original `DB_*` variables. The orders service accepts `JDBC_DATABASE_URL` or `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`; it also requires `USERS_API_URL`. Products uses `DB_*` variables. Set `ALLOWED_ORIGINS` on each API to permitted browser origins.

## Verification

- `npm ci --prefix frontend && npm run build --prefix frontend && npm run lint --prefix frontend`
- `mvn -f orders-service/pom.xml package -DskipTests`
- `php -l products-service/public/index.php`
- Install Python users-service requirements and `requests`; start an isolated stack, then run `python tests/integration.py`. Override `USERS_URL`, `PRODUCTS_URL`, `ORDERS_URL` for a test deployment. This test creates two test accounts and one demo order and leaves them in that database.

The HTTP integration test checks the catalog, duplicate registration, invalid passwords, session verification/logout, saved orders, trusted server pricing, customer order isolation and rejection of customer admin actions. After hosting, verify each `/health`, register/login through the website, save an order, and check it remains visible after reloading.
